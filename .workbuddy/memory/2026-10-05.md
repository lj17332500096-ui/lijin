## 2. `ci_shard` 判据四版迭代：最隐蔽的一次误判

**现象**：全量跑红`test_heavy_test_does_not_share_shard_with_crowd`
（`327.979 != 328.706`，各片 `[328.0, 327.9, 328.7, 327.7]`），**单跑绿**。

**取证过程**：
1. 确认 `_cost_of` 只依赖 `path.stat().st_size`（确定量），且全仓库无测试会改写
   `HEAVY_TESTS` 或在 `tests/` 增删文件 → 输入本应确定。
2. 实测当前文件集（129 个）：各片 `[329.4, 328.5, 328.5, 328.6]`，host 恰好是 max，差 0.0。
   **同一份代码两次运行结论相反**。
3. 权重扫描：w=60→host−max(other)=0.736；w=5→0.145；w=0→0.064。
   **判据的区分度只有 0.7，而 `places=1` 容差 0.05**。
4. 构造性实验（临时目录 10×20KB + 1×1KB）给出真相：
   w=60 压力用例**独占一片**（n=1）；w=0 与 2 个文件混在一片（n=3）。

**根因**：v3 判据「所在片总代价 == max」**拿被测算法自己的优化目标当判据**。
`shard()` 是贪心**均衡**算法，各片总代价必然接近（极差 0.9）⇒ 这是个随机翻转的布尔量。
真实机制是「rank 1 ⇒ 第一个被分配 ⇒ 落入空片」，与「各片代价谁最高」无关。

**四版对比**：

| 版 | 判据 | 为什么不行 |
|---|---|---|
| v1 | 所在片 ≤30 个文件 | 把「分片总数」与「分片大小」耦合，126→128 文件即全红 |
| v2 | 文件数 ≤ 其它片中位数 | 129/4≈32 均匀分布，咬不住，中和实验全绿 |
| v3 | 所在片总代价 == max | 量级被贪心算法抹平（0.9 vs 容差 0.05）→ 随机翻转 |
| **v4** | **代价排名第 1** | ✅ 无量纲无阈值；对权重敏感（60→1名/5→11名/0→17名） |

**拆成 4 条断言**：
- `test_heavy_test_is_the_most_expensive_file`（排名判据 + 领先 >5.0 裕度）
- `test_heavy_ranking_is_caused_by_the_weight_not_by_luck`（**中和实验固化成常驻测试**：
  权重归零后排名必须掉下去，反证上一条绿是权重挣来的；改`HEAVY_TESTS` 须 try/finally 还原）
- `test_heavy_weight_actually_isolates_the_stress_file`（**构造性验证「排名1⇒独占」推论**，
  临时目录造文件集，不依赖真实文件数 ⇒ `shard()` 哪天改成 round-robin 也会被咬住）
- `test_heavy_test_is_not_duplicated_across_shards`（原断言保留）

**中和实验 4 组注入全部精确报红**：权重 60→5、60→1、名字打错（重命名未同步⇒权重静默失效）、
`shard()` 改 round-robin（由构造性用例抓住）。

**新增铁律**：判据最终形态优先选**全序量（排名/次序）**而非带阈值连续量；
验证判据稳定性不能靠重跑（那是运气），要靠**注入扰动看它翻不翻**。

（运维的 `FORGE_APPROVAL_FAILCLOSED=off`、显式的「未声明 unattended」都会被
`.env` 里的残留值改回去），fail-closed 护栏静默退化，**且不报任何错**。
**现有测试无一覆盖该参数。**

新增 `tests/test_dotenv_precedence.py`（5 条），其中「反向」那两条是关键：
- `test_real_env_wins_over_dotenv`：`.env` 不能覆盖真实 env
- `test_dotenv_fills_gap_when_env_absent`：反向 —— `.env` 必须**仍能填空**，
  否则「完全不再加载」也无人发现
- `test_unattended_declaration_cannot_be_downgraded_by_dotenv`：空串与未设同义
- 2 条 `FORGE_RUNTIME_DIR` 解析（绝对 / 相对须锚到 PROJECT_ROOT）

**判据方法**：测**可观测行为**（子进程里 `os.environ` 最终值）而非 grep
`override=False` 字面量 —— 后者只证明文本在，不证明语义在。必须子进程：
`.env` 加载与 `RUNTIME_ROOT` 求值都在 import 期。

**中和实验 2 组**（均精确报红，报错信息直述危害）：

### 11.2 我今早的撤销错在哪（双重错误）

2. **归因对象错了**：我把它归到"点击用例 + `pilot.pause(0.1)` 定时不足"。

**不是加大 0.1** —— 那只是把概率红变成概率红但更慢，机器一慢又挂。

**验证（判据对缺陷敏感）**：负载下（3 个压测进程）
- 修前：6 次里 **3 红**（约 50%）

### 11.4 更正后的铁律
**「无源结论要撤销」的第一形态（结论从未有源）要撤销；
第二形态（结论曾经有源但**取样时负载不足**）不能撤销。**

**flaky 的证伪需要「在会触发它的条件下复现」，不是「在不会触发的条件下跑通」。**

## 13. 记忆探针的判据迭代（第 4 次「判据不可靠就改」的实例）

`tests/test_stale_memory_probes.py` 的矛盾检测判据，本轮共发现**三个独立缺陷**。
前两个我以为在调正则（症状），实际**谓词本身是错的**（病因）。

### 13.1 缺陷一：判据方向整体写反（最隐蔽）
初版：`ok and _claims_unsourced` ⇒「取证说已修 + 记忆说无源 ⇒ 矛盾」。
**这个组合根本不是矛盾** ——「我曾把它当无源撤销、后来证明是真问题并修好了」
是正确且有价值的纠错记录（MEMORY.md §2.1 记的正是这件事），按初版反而会报错。
**判据把正确的记忆判成错的。**

这个缺陷比「注入没生效」隐蔽得多：它**确实有鉴别力**（会红），只是鉴别的是
**错的方向**。若只做「能不能红」的中和实验，完全发现不了 —— 必须同时验证
「合法组合不得报红」。

修正后是一对**镜像**判据：
- `stale`：条目说「待修」+ 取证说「已修」⇒ 该划没划 ⇒ 报红
- `contradictions`：条目说「无源已撤销」+ 取证说「还没修」⇒ 被掩埋 ⇒ 报红

### 13.2 缺陷二：`retire_marks` 全文裸子串匹配 ⇒ 恒真
`test_tui_artifacts` 的 mark 含 `「无源」`，而「无源」在铁律正文出现 **3 次**
⇒ `_entry_is_retired` 对该 keyword **恒为 True**，与条目内容完全脱钩。
**恒真的判据不是「宽松」，是「无鉴别力」。**

根因分类：**撤销标记 ≠ 撤销理由**。「无源」是理由（不保证条目真被划掉），
「已撤销/已修/不成立」才是完成态标记。把理由塞进标记表 ⇒ 恒真。

自检手法（可复用）：把判据的每个输入分别替换成「与被测对象无关的常量」，
若判定结果不变 ⇒ 该判据恒真。

### 13.3 缺陷三：`_context_block` 只取首处锚定
`test_tui_artifacts` 在 MEMORY.md 出现 **4 次**，前 3 次都在**铁律正文的举例**里
（L77 讲两种形态、L91 讲取样负载、L100 讲用例名≠根因），真条目在 **L96**。
只取首处 ⇒ 判据永远读不到被测对象。
**同源教训**：与 §2.1「可达性要按调用点判、不能按函数名判」完全一致 ——
按名字/按首次判定会让第一次的命中掩盖其余各次。

## 15. 首跑真因：workflow 表达式语法（GitHub 连注释一起求值）

拿到用户提供的 annotations 后定位（**这是首跑的真正结论，§14 的猜测全错**）：

    Invalid workflow file: .github/workflows/ci.yml#L1
    (Line: 103, Col: 14): An expression was expected

### 根因
`ci.yml` 的注释里写了**双花括号表达式的字面量示例**（本意是说明
「runner 会把表达式求值后文本替换」），而 **GitHub 对 `run:` 块做表达式求值时，
注释也不例外**。解析器读到不完整的表达式 ⇒ 报错 ⇒ **整个文件被拒绝执行**
⇒ `completed/failure` 但 **jobs=0/ check-runs=0 / 耗时同一秒**。

第二处：`ci.yml:25` 注释里为说明历史 bug，写了含**减法运算符**的表达式
（GitHub 表达式**没有减法运算符**）。

1. **先怪反引号**：以为是 PowerShell 续行反引号紧跟表达式造成词法截断
   ⇒ 改成单行，actionlint **仍报红**。假设被实测否掉。
2. **注释是第二现场**：单行改完仍红 ⇒ grep 出**三处**双花括号，
   才看清「注释里的字面量」才是根因。**只修代码不动注释 = 没修。**

### 工具：actionlint 1.7.12（GitHub 官方同款解析器）
**下载姿势（本机网络环境）**：`github.com/.../releases/download` 被拦

`Accept: application/octet-stream` 可下（HTTP 200）。
已放 `C:\Users\Administrator\actionlint\actionlint.exe`。

## §18 CI 第四次首跑（run 37322670028）：shard 0 全绿，shard 1/2/3 仍红

**中和实验（双向验收）2/2**：

### 根因 A：我的护栏自己 portability 崩了（`WinError 2`）
`tests/test_path_normalization_symmetry.py` 硬编码 `.venv/Scripts/python.exe`。
**CI 上没有 `.venv`**（用 `actions/setup-python` 的 hostedtoolcache 解释器）⇒
`FileNotFoundError: [WinError 2]` ⇒ 判据自身崩。**本地有 venv 永远发现不了**
—— 典型「本地绿 = 假绿」。修法：改 `sys.executable`（两边都对）。
**教训：判据里凡引用「解释器/运行时绝对路径」都是 portability 雷**。

### 根因 B（真 bug）：FTS5 对中文恒失效，被向量掩盖
`tests/test_sources_rag.py` 两条：`index_source_file`「**不抛业务异常**」，
测试丢弃返回值 ⇒ 失败被静默吞掉，只表现为 `retrieve` 返回 `mode='no_results'`。

**逐层实测**（`var/_exp_docxprobe.py`，每层都打返回值）：
```
[INDEX-RET] ok=True chunks=1        ← 索引写入成功
[LEXICAL]  n=0 err=False            ← FTS 全文检索返回 0
[RETRIEVE] mode='hybrid' count=1← 靠向量兜住了
```
**最小复现（决定性）**：FTS5 `unicode61` 把中文**整段当一个 token**。
内容「按钮必须放在右下角且带确认弹窗。」：
```
'"按钮"' 0 hits / '"确认弹窗"' 0 hits / '"右下角"' 0 hits
'"按钮" OR "确认弹窗" OR "右下角"' 0 hits
```
⇒ **不是查询写法问题，是分词器问题**，任何查询侧改法都无效
（二元组 OR 查询同样 0 hits，已实测）。

**关键发现**：`rag.py` **压根没用 FTS5** —— 它用纯 Python 倒排 + BM25
（`_bm25_rank` / `_tokens` 对中文产相邻二元组），**中文一直正常**。
`sources/retriever.py` 走真 FTS5 ⇒ 中文中枢失效。**两套检索实现，一套好一套坏。**
`tests/test_rag.py::ChunkTests::test_tokens_cover_chinese_bigrams` 早就在测
rag 侧二元组，但 **sources 侧从没被这样测过** ⇒ 缺陷范围就这么大。

**为什么 CI 才暴露**：`requirements.txt` **无 onnxruntime**，模型目录
`models/bge-small-zh-v1.5` 也不入库 ⇒ **CI 上向量必然不可用** ⇒ 掩盖消失。

**中和实验（双向验收）**：
| 模式 | 修复前 lexical | 修复后 lexical | 修复后 retrieve |
|---|---|---|---|
| 向量 ON | 0 | 1 | hybrid count=1 |
| 向量 OFF（CI） | 0（`no_results`） | **1** | `lexical_only` count=**1** |

误伤方向：4 条无关查询（「量子力学入门书籍推荐」/「红烧肉的做法」/
`zzzqqqxyz`/`-volcano-`）**全部 `no_results`**，无误伤。

**修法**：`sources/retriever.py` 增 `cjk_bigrams()` + `_python_lexical_search()`
（Python 侧 BM25，与 `rag.py::_bm25_rank` 同策略），FTS5 仍作主路（英文有效），
两路按 `cid` 去重合并；`sources/store.py` 增 `all_ready_chunks()`。
**不改 FTS5 建表** ⇒ 不需重建索引、不升INDEX_VERSION。
