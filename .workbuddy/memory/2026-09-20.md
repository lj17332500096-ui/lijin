### ⚠️ 第 2 层 0 触发是"正确"的 —— 但正因如此才暴露真问题

用评测库真实 `arguments_json`（`invocation_id` 与基线逐调用对齐）离线重放
**生产同款** `repeat_target_key`：

```
达到 cap=3 的目标组数    : 3   （T020/T029/T044 各 1 个）
护栏若生效应拦下的次数   : 0
```

→ 全 374 次调用里，**同工具同目标同参数最多只出现 3 次**，而 cap=3 的语义是第 4 次才拦。
护栏逻辑没错，它**正确地**没什么可拦。

**它看不见的是这两种形态**（这才是真实空转）：

1. **空参数调用**：`T038` 的 `list_workspace_files` 传 `{}` → `args.get("directory")` 空
   → `repeat_target_key` 返回 `None` → **连计数都不进**。19 次调用反复列同一默认目录。
2. **参数持续漂移**：`T014` 的 15 次 `list_workspace_files`，`directory` 在
   `benchmark_fixture/app` → `my_creative_agent` → `benchmark_fixture` →
   `my_creative_agent/benchmark_fixture/app` … 一路换写法，**从不真正重复** → key 每次不同。

→ **结论：目标身份完全由参数推导，而模型空转恰好发生在"参数缺失"或"参数漂移"时。**
`readiness_gate.py:567-572` 注释声称覆盖"list 同一目录 3 次 / 同一 query 改词再搜 /
list↔search 来回"，**实现一种都没覆盖**（注释 ≠ 实现，又一处）。

# 第三轮：50 case 对照跑完 → 挖出评测器双倍计数 bug

## ⚠️⚠️ 最重要的发现：报告口径 = 2 × 真实调用数

对照跑完（`runs_eval_after_guard_fix/`，21m05s），Behavior Pass **46.0%**（基线 50.0%）→ 看似改坏。
排查退化 case 时发现：**报告的 `tool_calls` 恰好是基线 json 的 2.00 倍**
（全 50 case 无一例外；总和 748 vs 374；T040 = 24 vs 12）。

**根因** `benchmark/evaluator.py::observation_from_raw` 同时累加了两份数据：

```python
for item in raw.get("tool_calls") or []:            # 明细列表
    calls.append(_norm_tool_call(item))
for name, count in (raw.get("_exec") or {}).items():   # ← 同一批调用的聚合计数表
    for _ in range(int(count)):
        calls.append({...})
```

`_exec` 就是 `tool_calls` 明细的聚合 —— **同一事实的两种表示被当成两份事实相加** →
每个调用被计两次 → `tool_count` 判据（如 `[1,12]`）被污染成事实上的 `[1,6]`，
"实际只调了 7 次"的 case 被判超限失败。

**修复**：明细优先；明细缺失才退回计数表；`_blocked` 始终追加（明细里本就没有）。

**影响（同一批数据重算，确定性，无需重跑）**：

| | 修正前 | 修正后 |
|---|---|---|
| 基线 Behavior Pass | 50.0% | **68.0%**（+18.0pp） |
| 护栏修复组 Behavior Pass | 46.0% | **72.0%**（+26.0pp） |

→ **光修这个计数 bug，基线就提升 18pp**。这是本轮最高杠杆项，且**不涉及行为改变**。
