## §28 从「仓库根污染」到「沙箱逃逸」：一次排查挖出三层问题

起点是仓库根出现 101 个未跟踪垃圾文件（随机 8 字符名、每个 4 字节、内容 `blat`）。
追查结论层层升级，每一层都由**实测**而非推理坐实。

### 第1 层：代码执行污染工作区
- `code_exec.py::_project_dir()` 受信分支 `return root` + `run_python` 把 LLM 生成代码写成
  `base_dir/_inline_*.py` 并以 `cwd=base_dir` 执行 ⇒ 生成代码里的
  `tempfile.mkstemp(prefix='', dir=os.getcwd())` 落在工作区。
- 指纹定性：800 字符全落在 `a-z0-9_`（37/37 全出现、零越界、χ²=40.27）= `tempfile._RandomNameSequence`；
  且 `mkstemp` 默认加 `tmp` 后缀，**只有 `prefix=''` 才产出裸 8 字符**。
- ⚠️ 8字符名是 `prefix=''` 的**特有**产物 —— 不是随机名，是「有人故意不写前缀」的指纹。

### 第 2 层：pathlib 路径丢弃 = 生产模式下的沙箱逃逸（HEAD 原有）
```python
return (SANDBOX_ROOT / proj).resolve()   # 旧末行
```
`Path('F:/ws/code_sandbox') / 'F:/tmp/x'` == `F:\tmp\x` —— **右操作数是绝对路径时左操作数被丢弃**。
⇒ 任意绝对路径型 project 可把 cwd 指向磁盘任意位置，**不需要受信根、不需要 `FORGE_TEST_MODE`**。
- `git show HEAD:code_exec.py` 确认 HEAD 就有 ⇒ **非本次引入**，是预先存在的安全缺陷。
- 「只在评测模式发生」这个前提**不成立**（我最初也是这么判的，被验证者推翻）。

### 第 3 层：目录级 junction/symlink 逃逸
只取末段名字 + `.resolve()` **仍不够** —— `.resolve()` 会**跟随 symlink/junction**：
① 一次 `run_python` 生成代码执行 `mklink /J code_sandbox\stage2 <仓外目录>`（junction **不需要管理员权限**）
② 第二次 `project="stage2"`（纯项目名，过字符白名单）⇒ 落点仓外。
- `write_code_file`/`read_code_file`/`list_code_files` 走同一条路且**不需要 `ALLOW_CODE_EXEC`**（门槛更低）。
- 已验证的边界：文件级 symlink 被 `_file_target` 拦住；junction 指向 `BASE_DIR` 被 `_safe_workdir` 拦住。
  漏洞精确限定为「**目录级** symlink 指向 `BASE_DIR` **以外**」。
- 修法：`_path_is_within()` 用 `os.path.realpath()` + `normcase` + **分量级** `relative_to`比较；
  越界返 `None` 而非回退到固定目录（回退目录自己可能就是 junction，等于把洞换位置）；
  **本函数只算路径不创建目录**（`mkdir` 在调用方）⇒ 无「先建后校验」的 TOCTOU 窗口。

### 逃逸被真实使用过的证据
`F:/tmp` 下 200 个同批 `blat`，时间戳 `2026-10-06T06:35` 与仓库根100 个**同分钟**、md5 相同
⇒ 那次运行的工作目录**至少有两处**。

## §29 今天栽的三个坑（都是新失败模式）

### 坑 1：我自己写的护栏，自己恒绿
`TestSideSymmetryTests` 用正则扫 `setUp`/`tearDown` 源码里有没有出现过 `rag._EMBEDDER` 这个词。
实测 5 种退化写法**全部通过**：自赋值 `rag._EMBEDDER = rag._EMBEDDER`（语义=不清）、
只读 `x = rag._EMBEDDER`、写在注释里、挪进 helper 方法、**完整删除**（反而会失败，只因词都没了）。
- 根因：**文本匹配只能问「词出现过吗」，问不了「赋的是不是 None」**。
- 修法：改**行为判据** —— 预置脏态（假引擎 +脏 error + LOADED=True）→ 真调 `setUp()` →
  断言三全局真被清。配套三个对照类（正确写法 / 缺陷写法 / 完全不碰开关）让判据双向自证。
- ⚠️ 旧判据与新判据在**同一种退化**（自赋值）上表现相反：旧 19 passed全绿 / 新 2 failed。
  这是判据有没有鉴别力的**唯一可靠试金石**。
- ⚠️ 子串坑：`assertIn("rag._EMBEDDER", src)` 会被 `rag._EMBEDDER_LOADED` 满足 ⇒ 必须词边界正则。

### 坑 2：给 worker 的修法本身是错的，被驳回两次
- 第一次：让「`resolved` 等于受信根本身时回落」—— 污染场景传的是纯项目名 `"my_creative_agent"`，
  走 **basename 匹配分支**，那里 `resolved` 根本没被用到，条件恒为假，**撤了等于没撤**。
  且若强行加到 basename 分支会**误伤**正常 benchmark 评测（受信根=fixture、project=该根自身时
  `resolved` 确实==root）。正确判据是「受信根是否等于 `BASE_DIR`」。
- 第二次：让「用 `SETTING=""` 探测声明关向量的类」—— 但 `rag.py:173` 在 `SETTING=''` 时返回
  `EMBED_DEFAULT_DIR.is_dir()`，而 `models/` **不入库** ⇒ CI 上恒 False ⇒ **探测前提在 CI 上不成立、
  判据静默失效**。正确做法：用**显式非空路径**走 `rag.py:171-172` 分支（与磁盘无关）。

### 坑 3：确认注入生效 ≠ 注入语义等价于目标缺陷
worker 写探针时，第一版**追加**退化语句而非**替换**，5 种退化全显示「通过」，

- 两个失败模式要分开验：① 改动在不在（grep/读回/md5）② 改动的语义是否等于目标缺陷。

### 坑 4：worker 实验残留会污染后续测试（我的编排失误）

## §30 归因错位：产品缺陷 vs 测试缺陷

修`rag.py::_try_load_embedder` 时我把归因写反了。
- 交叉实验（我独立复核过一遍）：**产品侧修好 + 测试侧保留缺陷 ⇒ 22 passed 全绿**；
  反向（产品侧保留 + 测试侧修好）也全绿 ⇒ 两侧修法**各自都能独立让测试变绿**。
- `grep '_EMBEDDER_LOADED\s*=\s*False'`：除 `rag.py` 模块初始化外**全在 tests/** ⇒
  该自相矛盾态**生产不可达，只可能由测试触发**。
- 结论：真根因是**测试隔离缺陷**（`setUp` 只重置标志位、漏了 `_EMBEDDER` 对象）；
  产品侧那两行是**第二道防线**（把「LOADED 为真⇒三全局自洽」变成模块不变量，
  而非依赖「没人会去置 False」的巧合）。
- **护栏 docstring 写「实测后果=hybrid 的根」会把两者混为一谈**，已改为三段式归因。

### 顺带查出的原有缺陷：加载失败返回「半成品 engine」
`rag.py` 的 `except` 分支里 `engine` 在 `load()` 抛异常前已赋值，`_EMBEDDER` 却仍是 `None`
⇒ 返回值非 None 而全局是 None ⇒ 调用方 `if engine is None` 误判成功 → 对半成品调
`embed_batch` → **工具抛未捕获异常**。`build()` 与 `search()` 均实测复现。
- 触发条件：装了 `models/` 但 `onnxruntime`/`tokenizers` 缺失或模型损坏（**常见用户环境**）。
- `git show HEAD:rag.py` 确认 HEAD 已有 ⇒ 原有缺陷，非本次引入。修法：`except` 里加 `engine = None`。

## §31 归因方法论补充（本轮新增）

- **「既有失败」必须先隔离外部现场、再对比 HEAD**，顺序不能反。我在全量看到 6 条红时，
  第一反应是「是不是我改的」，其实是自己 worker 的实验残留。
- **「单跑绿」不能证明条件相关问题的存在**。`InlineFileCleanupTests` 普通环境 5 passed，
  只在护栏构造的 **8.3 短名 tempdir** 下失败 ⇒ 必须在那个条件下复现。
- **8.3 短名根守门名单是有意维护的清单**：出问题**不能把它从名单里删掉**来"修好"，那是掩盖。
  本轮真因其实是残留物（字面名 `%SystemDrive%` 目录树，某外部组件把未展开环境变量模板
  写进了 CWD），不是路径写法不对称。
- **判「是不是本轮产生」看 mtime 与开工时间的关系**：仓库根同款残留 mtime 11:00 < worker 11:21 开工
  ⇒ 非本轮引入。
- **`datetime.now()` 分辨率实测约 1.6ms** ⇒ 12 并发只产生 5 个文件名、7 调用崩溃（`PermissionError`）。
  临时文件命名**不能只用时间戳**，要用 `tempfile.mkstemp`。
- **Windows 保留设备名**（`CON`/`NUL`/`PRN`/`AUX`/`COM1`）要大小写不敏感地过滤，
  且`_CON__` 这种带前缀+哈希的形态才不会撞设备名。
- **只取末段名字会致project 名碰撞**（`a/b` 与 `b` 共用目录 ⇒ 可跨 project 读文件）。
  修法：末段名 + **稳定哈希后缀**（既收敛路径又可区分）。
- **拆函数是清理逻辑的正确前提**：原 `run_python` 执行段有 4 个 `return`，逐个手写
  `finally` 必漏 ⇒ 抽出 `_run_python_file()`。
- **用户指定的既有文件绝不能被清理**：用 `inline_tmp` 标记区分「本次生成的临时文件」
  （`filename` 分支恒 `None`）⇒ 用户自建的 `_inline_*.py` 不会被删。
